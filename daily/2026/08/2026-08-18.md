Phase 2 主要解决了历史行情的获取、验证和原始保存：

```text

```

Phase 3 将这条链路扩展为：

```text
IBKR
→ fetch
→ validate raw
→ save raw
→ processing
→ validate processed
→ save processed
→ reload
→ validate
→ consistency check
```

这次升级的重点不只是“能够可靠地拿到和保存行情”，而是开始建立稳定、统一、与具体数据源解耦的 processed market data layer，为后续指标、策略、回测和风险模块提供统一的数据接口。

## Validation、Processing 与 Storage 的职责边界

今天进一步理解到，数据链路中的三个模块虽然会接触同一份数据，但它们解决的是不同问题。

### `validation.py`

Validation 判断一份数据能否被合法解释和使用，例如：

- 输入和字段结构是否正确
- 日期能否转换为合法日期
- OHLCV 能否转换为数值
- high、low 等领域规则是否成立

验证过程中可以临时调用 `pd.to_datetime()` 或 `pd.to_numeric()` 来判断内容是否可转换，但它不负责生成正式的标准化数据集。

### `processing.py`

Processing 真正把数据转换为项目统一标准。它返回一份新的 DataFrame，不修改传入的 raw DataFrame，并统一：

- schema
- dtype
- 日期顺序
- index

因此，即使 validation 和 processing 都可能调用 `pd.to_numeric()`，也不是无意义的重复：

```text
validation：检查数据能不能成为数字
processing：正式将 processed 数据统一为规定的数值类型
```

### `storage.py`

Storage 负责路径、保存和读取。它不承担字段标准化或市场数据业务规则，否则存储逻辑会与某一种数据结构过度耦合。

今天形成的认识是：判断合法、执行标准化和负责持久化是三种独立职责。拆分这些职责后，每个模块的行为更明确，也更容易分别测试和修改。

## Raw Data 与 Processed Data 分层

`raw` 层尽量保留数据源返回的原貌，用于追溯问题、定位异常，以及未来在 processing 规则改变后重新处理数据。

`processed` 层保存项目统一标准后的数据，是后续研究、指标、策略和回测真正应该消费的数据层。

这层边界也降低了下游模块对数据源的依赖。将来无论接入 IBKR、Yahoo、Polygon 或其他数据源，只要最终都转换为相同的 processed schema，下游模块就不需要关心原始数据来自哪里、原始字段如何命名。

标准 processed schema 为：

```text
date, open, high, low, close, volume
```

因此，processing 可以理解为数据源与未来研究、回测模块之间的标准化中间层。

## `process_market_data()` 的处理流程

今天完整理解了 `process_market_data()` 的主要执行顺序：

1. 检查输入是否为 DataFrame
2. 检查标准必要字段
3. 选择标准列
4. 创建独立副本，避免修改 raw 输入
5. 转换并标准化日期
6. 将 OHLCV 标准化为数值类型
7. 按日期稳定排序
8. 重置 index
9. 拒绝重复日期
10. 再次执行 validation
11. 返回标准化后的新 DataFrame

其中：

```python
processed = frame.loc[:, MARKET_DATA_COLUMNS].copy(deep=True)
```

`.loc[:, MARKET_DATA_COLUMNS]` 表示保留全部行，只选择标准列；`.copy(deep=True)` 则创建独立副本，保证 processing 不会意外修改 raw 输入。这不只是 pandas 写法，也是 raw 与 processed 职责边界在代码中的体现。

## 今天加深理解的 pandas / Python 操作

### 日期标准化

原始日期即使显示为 `2026-08-13`，也可能仍然是字符串。`pd.to_datetime(..., errors="coerce")` 会尝试转换日期，并将非法内容变为日期类型中的缺失值 `NaT`。

`.dt.tz` 用于检查 datetime Series 的时区信息。当前日线 processed schema 不接受带时区的日期，因此遇到有歧义的时区数据时应明确报错，而不是静默转换。

通过：

```python
.astype("datetime64[ns]")
```

可以将 processed 的日期列统一为标准 datetime 类型。

### OHLCV 数值标准化

`pd.to_numeric(..., errors="coerce")` 会把可解释的内容转换为数值，把无法转换的内容变为 `NaN`。Processing 最终将 OHLCV 统一为 `float64`，使来自不同数据源的行情在进入 processed 层后保持稳定 dtype。

对于二维 OHLCV 区域：

```python
.isna().any().any()
```

第一次 `.any()` 按列判断每列是否存在 True，第二次再判断所有列中是否至少有一列存在 True，从而检查整个区域中是否出现缺失值或无法转换的数值。

### 排序与索引

```python
.sort_values("date", kind="stable")
```

会按照日期重新排列整行数据。`stable` 保证相同排序键记录的相对顺序稳定，但项目仍然不允许重复日期存在。

排序后，旧 index 不会自动变为从 0 开始的连续索引，因此还需要：

```python
.reset_index(drop=True)
```

`drop=True` 表示直接丢弃旧 index，不把它保留为普通列。最终 processed 数据使用从 0 开始的 `RangeIndex`。

### 重复日期处理

```python
processed["date"].duplicated().any()
```

用于判断日期列中是否存在重复值。项目选择遇到重复日期时直接抛出 `ValueError`，而不是调用 `drop_duplicates()` 静默删除。

这是因为当前没有可靠依据决定应该保留 first 还是 last。在量化数据中，缺乏规则时静默“修复”脏数据，可能比明确失败更危险。

### 使用位置取得日期边界

`_date_bounds()` 使用 `.iloc[0]` 和 `.iloc[-1]` 按位置取得第一条和最后一条日期。由于 processing 已经保证数据按日期从早到晚排序，因此首尾记录可以用来表示数据的日期范围。

## Validation 与 Integrity / Consistency

今天明确区分了两个容易混淆的问题。

Validation 回答的是：

> 这份数据本身是否合法？

例如字段是否完整、日期和 OHLCV 是否有效、价格关系是否符合业务规则。

Integrity / Consistency 回答的是：

> 数据经过 save → load 后，是否仍与保存前保持一致？

项目目前通过行数和日期范围进行基础 round-trip consistency 检查。即使重新加载的 `loaded_history` 能通过 `validate_market_data()`，也不代表持久化过程一定没有丢失数据。

例如，保存前有 251 行，加载后只剩 250 行。剩余的 250 行仍可能全部合法，因此能够通过 validation，但整份数据已经不完整。这说明“每条数据都合法”和“保存前后数据一致”是两个不同层次的保证。

## Processing 测试与数据契约

今天开始系统理解 `tests/test_processing.py` 的作用。测试不只是确认函数能否运行成功，而是把 processed schema 的要求变成可重复执行的合同。

测试覆盖的关键约束包括：

- 标准列及列顺序
- 日期升序排列
- 使用从 0 开始的 `RangeIndex`
- date 使用标准 datetime dtype
- OHLCV 使用 `float64`
- processing 不修改输入 DataFrame
- 拒绝非 DataFrame 输入
- 拒绝缺少必要字段的数据
- 拒绝无效或缺失日期
- 拒绝带时区日期
- 拒绝非数值 OHLCV
- 拒绝重复日期

`pytest.raises` 用于测试代码是否抛出了预期异常；如果本应拒绝的数据没有触发异常，测试反而失败。`match=` 还可以检查异常信息是否符合预期。

今天新学习的 `pytest.mark.parametrize` 并不是专门用于异常测试，而是让同一个测试函数使用多组参数重复执行。例如将 `open`、`high`、`low`、`close`、`volume` 作为参数，可以让同一项非法数值测试分别覆盖五个字段，减少重复代码，也更方便以后扩展和维护。

## 今天形成的工程化理解

经过今天的梳理，我对 Phase 3 建立了以下认识：

1. 合法的数据不一定已经标准化。
2. 已经标准化的数据，也不能证明 save / load 后仍然保持完整一致。
3. Validation、Processing、Storage 和 Consistency Check 分别解决不同问题。
4. Raw / Processed 分层提高了数据的可追溯性，也为重新处理保留了原始依据。
5. Processing 是数据源与未来研究、策略和回测模块之间的标准化中间层。
6. 自动化测试不仅检查当前 bug，也长期保护 processed schema 和数据契约。
7. 没有可信处理规则时，脏数据应显式失败，而不是被静默修复。
8. 不同模块中看似相似的转换操作，只要目的和职责不同，就不一定应该合并。

完整的数据链路可以概括为：

```text
Broker
→ Validation
→ Raw
→ Processing
→ Processed
→ Storage
→ Reload
→ Validation
→ Consistency
→ Future Research / Backtest
```
